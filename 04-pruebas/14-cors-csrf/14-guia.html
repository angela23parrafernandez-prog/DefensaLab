Antes de comenzar

Herramienta: ZAP y navegador · Descarga y documentación oficial

Datos que debes preparar: URL/IP del entorno de pruebas, versión, autorización, usuarios ficticios con roles relevantes y evidencia de respaldo. En ZAP, las etiquetas pueden variar según versión y traducción.

Seguridad: realiza estas pruebas únicamente sobre aplicaciones propias o autorizadas, en preproducción, con datos sintéticos. No realices cargas masivas ni pruebes sistemas externos.

Pasos exactos

Cada instrucción aparece en español y debajo, en letra más clara y pequeña, el nombre de la opción en inglés. Marca cada paso cuando lo completes.

  1. English UI: Application → Cookies
    Comprobar: Se determina si CSRF aplica.
  2. English UI: History → Open/Resend with Request Editor
    Comprobar: Se muestra la solicitud.
  3. English UI: Request / Response Headers
    Comprobar: No se autoriza cualquier origen con credenciales.
  4. English UI: Request Editor → Send
    Comprobar: El servidor rechaza solicitudes no autorizadas.
  5. English UI: Not applicable
    Comprobar: La decisión se justifica por arquitectura.

Interpretación de resultados

Correcto

El control se aplica y existe evidencia reproducible de la respuesta esperada.

Hallazgo potencial

Se observa una respuesta anómala; confirmar permisos, condiciones y alcance antes de clasificar.

No concluyente

Faltan cuentas, permisos, logs o condiciones para confirmar el resultado. Registrar limitación.

Severidad orientativa

Crítica: compromiso masivo o control total demostrable. Alta: acceso indebido relevante o alteración de datos sensibles. Media: impacto limitado o condiciones adicionales. Baja: exposición menor. Determina gravedad según impacto, probabilidad y contexto; no por nombre de prueba.

Evidencias que debes guardar

Identificador del caso, fecha, versión, cuentas ficticias, petición y respuesta saneadas, captura, resultado esperado y real, severidad razonada, corrección propuesta y retest.

Retest

Después de corregir, verifica la nueva versión, repite los mismos pasos, compara las respuestas y registra «Corregido», «Persiste» o «No verificable».

Alertas principales: dónde verlas, cómo interpretarlas y cómo corregirlas

Los hallazgos siguientes son ejemplos posibles, no resultados confirmados. La gravedad definitiva depende del impacto, exposición y evidencia. No marques una alerta como vulnerabilidad sin reproducirla y descartar falsos positivos.

Cómo localizar las alertas en OWASP ZAP 2.17 (interfaz en español)

  1. En la parte inferior, pulsa «Alertas» (English: Alerts), junto a «Historial».
  2. Despliega el sitio y selecciona una alerta. Revisa Riesgo, Confianza, URL, Parámetro, Evidencia y Solución (English: Risk, Confidence, URL, Parameter, Evidence, Solution).
  3. Si no aparece una alerta, pulsa «Historial» (English: History), selecciona una petición de prueba y abre «Petición» / «Respuesta» (English: Request / Response) para una comprobación manual.
  4. Para guardar el informe, usa el menú superior «Informe» (English: Report) y la opción de generación de informes disponible en tu versión. Elige únicamente información saneada.

Interpretación: una alerta «Informativo» no equivale a riesgo alto; el código HTTP 200/201 tampoco demuestra que una operación sea segura. Los escaneos pasivos no detectan todos los fallos de lógica o autorización.

Clasificación del resultado

Conforme: el control funciona con cuentas y datos de ensayo. Hallazgo confirmado: se reproduce un incumplimiento con impacto demostrado. Posible falso positivo: la herramienta alerta, pero el contexto no confirma el riesgo. No evaluado: falta acceso, autorización o evidencia. No aplica: la funcionalidad no existe, con justificación documentada.

Registro y retest

Anota: ID de prueba, versión/commit, usuario ficticio y rol, URL saneada, pasos, respuesta esperada, respuesta observada, impacto, captura sin datos personales, recomendación, responsable y fecha de nueva verificación. Tras corregir, repite exactamente el escenario y comprueba que las funciones legítimas siguen operando.
