Objetivo y requisitos

Revisar un proyecto recibido como ZIP o mediante un repositorio Git, antes de autorizar la liberación de un módulo. No realiza escaneo automático desde DefensaLab.

Confidencialidad: trabajar con una copia autorizada. No pegar secretos ni código confidencial en servicios externos. Las herramientas se ejecutan localmente; la descarga de reglas o bases de datos puede requerir conexión.

Herramientas gratuitas y sin suscripción obligatoria para este flujo:

  • Gitleaks (código abierto, Windows y Ubuntu): descarga oficial.
  • Semgrep Community Edition (motor y reglas comunitarias gratuitos; Windows mediante WSL2 recomendado y Ubuntu nativo): instalación oficial. No utilizar funciones comerciales.
  • Trivy (código abierto, Windows y Ubuntu): instalación oficial.

Nota Windows: Gitleaks y Trivy disponen de binarios para Windows. Para Semgrep CE se recomienda WSL2 con Ubuntu cuando la instalación nativa no esté soportada por la versión elegida. No es una prueba «solo Ubuntu», pero esa parte puede requerir WSL2/Docker.

Preparar: carpeta del código, autorización, versión o commit, permisos para instalar herramientas, PowerShell y, para Semgrep, Python/WSL2 según la instalación seleccionada.

Pasos exactos

Marca cada paso al completarlo. Las casillas se guardan localmente en este navegador.

  1. Comprobar: Registrar ruta local, fecha, responsable y exclusiones.
  2. Comprobar: ZIP: la historia Git podría no estar incluida; documentar esta limitación.
  3. Comprobar: gitleaks version; semgrep --version; trivy --version. Si alguna falla, instalar desde los enlaces oficiales.
  4. Comprobar: Analizar coincidencias sin copiar valores secretos al informe. Guardar evidencia fuera del proyecto.
  5. Comprobar: La revisión de historial solo aplica si existe .git; no equivale a revisar el historial de un ZIP sin .git.
  6. Comprobar: Revisar reglas utilizadas y hallazgos; la configuración auto puede requerir descargar reglas. Para un entorno sin red, utilizar reglas locales previamente aprobadas.
  7. Comprobar: Revisar dependencias y archivos de configuración; las bases de vulnerabilidades requieren actualización previa y pueden necesitar acceso a internet.
  8. Comprobar: No ejecutar el código sospechoso ni reproducir credenciales; para secretos reales, solicitar rotación inmediata y revisar exposición.
  9. Comprobar: Si hay secretos en historial Git, rotarlos; borrar un commit no revoca credenciales.
  10. Comprobar: Anotar versiones de herramientas, alcance, exclusiones, pruebas omitidas y retest.

Si trabajas con Ubuntu o WSL2

Los comandos son equivalentes, cambiando rutas de Windows por rutas Linux. En la carpeta del proyecto:

gitleaks dir --redact --report-format json --report-path ../evidencia-gitleaks.json .
gitleaks git --redact --report-format json --report-path ../evidencia-git.json .   # solo con .git
semgrep scan --config auto --metrics off --json --output ../evidencia-semgrep.json .
trivy fs --scanners vuln,misconfig --format json --output ../evidencia-trivy.json .

Las opciones CLI dependen de la versión instalada; confirmar con --help. Las actualizaciones de reglas y bases de vulnerabilidades pueden necesitar red.

Cómo interpretar resultados

SeñalVerificaciónAcción
Posible secretoComprobar si está activo sin divulgarloRevocar/rotar y migrar a gestor de secretos
Patrón inseguro SASTRevisar origen, validación y uso de datosCorregir código y agregar prueba de regresión
Dependencia vulnerableConfirmar versión, alcance y aplicabilidadActualizar o mitigar con evidencia
Configuración inseguraValidar entorno y exposiciónAplicar configuración segura y retestar

Estados: confirmado, posible, falso positivo, no evaluado. No declarar seguro un componente porque el escáner no encuentre alertas.

Registro del hallazgo

Completar plantilla de hallazgo e informe de liberación. Registrar identificador, CWE, archivo, línea, evidencia sin secretos, impacto, severidad, solución y retest.
